# Reglas personales mínimas de Codex

- {{APROBADOR}} asigna el trabajo de cada WT. Al abrir un nuevo chat para continuar un WT, aplicar `$context-resume`: verificar Git y el handoff vigente, presentar pendientes y esperar «A, B u otro» antes de implementar.
- Al invocar `$context-handoff`, cerrar sólo el contexto del chat; conservar el WT y registrar una versión breve fuera del repo del producto.
- Registrar y respetar OWNERS en `~/.{{ARNES}}/projects/<identidad>/`. Sólo las skills `project-init` y `worktree-*` lo modifican; `context-resume` sólo verifica. Transferir trabajo usa commits identificables entre WT propios y no obliga PR ni merge a `dev`.
- Mantener como máximo cinco WT activos por proyecto y un único owner escritor por WT. Antes de crear o reactivar, contar las filas activas y verificar Git; preferir uno–tres WT salvo necesidad concreta.
- Antes de crear commits, cherry-picks que generen commits, PR, push o merge, validar la identidad Git contra PROJECT con `~/.{{ARNES}}/scripts/Verificar-Identidad-Git.ps1`. No inferir ni inventar emails `users.noreply.github.com`; si falta el valor exacto, detenerse y pedirlo.
- Si un agente levanta un dev server Next.js, usar `~/.{{ARNES}}/scripts/Iniciar-Sin-Deteccion-De-Agente.ps1` para evitar artefactos generados por detección de agente. No versionar `AGENTS.md`/`CLAUDE.md` generados por Next; antes de commit/push en proyectos Next ejecutar `~/.{{ARNES}}/scripts/Verificar-Artefactos-Agente-Next.ps1` y revertir `next-env.d.ts` si el único cambio es `.next/dev/types`.
- Un merge a `dev` requiere aprobación de {{APROBADOR}} y lo ejecuta el worker. Promover `dev` a `main` también requiere aprobación expresa de {{APROBADOR}}; sin ella no se ejecuta.

Estas reglas operativas se aplican a proyectos registrados en ~/.{{ARNES}}/projects/. Resolver la identidad por PROJECT, incluso después de agregar un remoto. La instalación compartida incluye PRINCIPIOS_DISENO.md, CONTRATO_HANDOFF.md, CRITERIOS_ENTREGA_PRODUCTO.md y templates/. Aplicar los criterios privados antes de preparar entregas del producto. Crear Issues sólo cuando la coordinación cruce WT o proyectos; transferencias y dependencias siempre la requieren. Usar el repositorio privado de PROJECT sólo para coordinación del proyecto. Las incidencias del arnés, skills, handoff, rescate de threads o comportamiento de Codex/Claude van a `{{ARNES}}`; si hay duda, preguntar antes de crear. Firmar toda Issue creada desde WT con `Proyecto del que viene`, `WT` y `Plataforma`, y notificar a {{APROBADOR}}.
