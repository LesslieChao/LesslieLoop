# Contrato de cierre y apertura del WT

Codex y Claude Code implementan el mismo contrato con `context-handoff` y `context-resume`. El ciclo de vida del proyecto y sus WT se administra por separado con `project-init`, `worktree-create`, `worktree-pause`, `worktree-reactivate`, `worktree-transfer` y `worktree-close`. {{APROBADOR}} observa manualmente el porcentaje de contexto: 70–75% sugiere buscar corte; por encima de 80% conviene no comenzar una fase nueva. Las skills no monitorean el porcentaje.

Rigen los [principios de diseño](PRINCIPIOS_DISENO.md): coordinación humana y determinista, estado mínimo y un máximo estricto de cinco WT activos por proyecto. La situación preferida es uno–tres; crear capacidad por anticipado no es un objetivo.

## Estado personal, fuera del producto

- Identidad del proyecto: al darlo de alta usar `<owner>/<repo>` de `origin`, sin `.git`, o `local/<nombre>` sin remoto. Conservar esa identidad cuando se agregue o cambie un remoto; no crear un segundo registro.
- Carpeta del proyecto: `~/.{{ARNES}}/projects/<identidad>/`. Resolverla por `PROJECT.md`: cotejar carpeta contenedora, checkout administrativo, directorio Git común o remoto; si hay más de una coincidencia, pedir dirección.
- `PROJECT.md` guarda identidad, perfil particular, identidad Git autorizada para commits, validaciones, revisión del arnés y destino privado de coordinación. La instalación se define en `docs/INSTALACION.md` del arnés, copiado a `~/.{{ARNES}}/INSTALACION.md`.
- Propietarios: `OWNERS.md` en esa carpeta, con filas `WT`, worker, ruta del WT, branch, responsabilidad y estado `activo`, `inactivo` o `cerrado`. Actualizar al crear, pausar, reactivar o cerrar un WT.
- Handoff actual: `WTxx/HANDOFF.md`. Historial: `WTxx/history/0001.md`, `0002.md`, etc. Toda escritura (alta, pausa, transferencia, cierre o rotación) crea una versión inmutable y actualiza la copia vigente con idéntico contenido; la primera es 0001.
- CodeGraph opcional: `codegraph/WTxx/` guarda mapas compactos privados generados desde Git para reducir lectura de contexto. No se copia al producto, no modifica OWNERS y no reemplaza handoffs ni Issues.

## Disposición local

Codex y Claude abren el proyecto sobre una carpeta contenedora, que inicialmente es vacía y no es un repositorio Git. `project-init` crea `repo/` como checkout administrativo y `worktrees/WT01 - Título/` como primer checkout de trabajo. Los WT siguientes viven en el mismo `worktrees/` y usan `WTxx - Título`. El título no identifica al worker: una transferencia cambia OWNERS, no la carpeta.

El primer chat operativo también usa la convención `00_[WT]_[NOMBRE]`. `project-init` debe renombrarlo si tiene una herramienta real para hacerlo; si no la tiene, deja indicado el nombre exacto como pendiente manual. El alta inicial no debe convertirse en una lectura completa del producto: primero genera CodeGraph, lee sólo su `resumen.md`, verifica Git, registra estado, identifica comandos de validación y consulta la documentación mínima necesaria para proponer A/B/u otro. Las especificaciones extensas, historiales o carpetas completas se leen después, cuando {{APROBADOR}} elige una tarea que las requiere.

Antes de ejecutar Git o modificar el producto, toda skill resuelve el ID solicitado en OWNERS, obtiene su ruta absoluta y comprueba con `git worktree list` y `git rev-parse` que pertenece al directorio Git común registrado. Abrir el chat desde la carpeta contenedora no autoriza a escribir en `repo/` ni en otro WT. El checkout `repo/` es administrativo y no es territorio de implementación.
- Si dos equipos necesitan continuar el mismo WT, sincronizar el estado personal y el estado Git antes de abrir otro chat. Un handoff local aislado no se propaga solo.

Los archivos de la raíz de **este arnés** rigen la evolución del arnés. Los proyectos generados sólo reciben `plantilla-proyecto/`; sus reglas permanentes personales se cargan desde Codex/Claude Code, no se copian al producto.

## Integridad del estado

Antes de actuar, leer PROJECT, OWNERS y sólo el handoff vigente del WT. Comprobar carpeta, worker, rama y HEAD contra Git. Git y los archivos reales prevalecen ante cualquier contradicción con un relato del agente; el estado local sólo conserva lo que Git no representa bien. Si el registro no existe, usar project-init o worktree-create; context-resume nunca repara ni crea filas. Un WT cerrado no se reactiva por inferencia.

Serializar las modificaciones de OWNERS entre workers. Releer inmediatamente antes de guardar, conservar filas ajenas y detectar ID/rutas/ramas duplicados. Si la creación Git falla, no registrar el WT como activo; si Git se creó y el registro falló, informar la carpeta y rama resultantes y completar esa misma alta al reintentar, sin crear otra.

Cada worker modifica y ejecuta pruebas sólo en su WT. Cada WT tiene un solo owner escritor y una lectura del registro común no autoriza a operar sobre el WT ajeno. Los cambios de responsabilidad se confirman con {{APROBADOR}} y quedan registrados; una rotación no los modifica ni reasigna una carpeta silenciosamente.

CodeGraph puede usarse para decidir qué archivos leer antes de una tarea, pero no se ejecuta por rutina al abrir un WT. Si se menciona en un handoff, registrar sólo ruta privada, `HEAD` cubierto y conclusiones mínimas. Si su análisis produce documentación útil para el producto, convertirla en documentación normal y sanitizada.

## Contexto SSH heredable

Cuando una sesión saliente ya usó SSH funcionalmente, el handoff puede registrar contexto operativo no secreto para que el sucesor no diagnostique falsos bloqueos. Registrar sólo el alias SSH usado, shell/binario que funcionó, si había `SSH_AUTH_SOCK` usable, tipo de agente observado (`PowerShell/OpenSSH` o `Git Bash/MSYS`) y un comando seguro de verificación. No agregar esta sección por rutina si el WT no usó SSH.

El sucesor debe comprobar primero ese mecanismo registrado antes de concluir que no hay agente activo. En Windows, distinguir un fallo de PowerShell/Windows OpenSSH de un acceso disponible vía Git Bash/MSYS. Si el socket, binario o alias ya no existe o no autentica, informar el bloqueo y pedir intervención del usuario.

Nunca guardar claves privadas, passphrases, contenido de `.env` ni secretos. No iniciar `ssh-agent` ni ejecutar `ssh-add` sin acción explícita del usuario. Esta regla sólo preserva una sesión ya habilitada; no amplía acceso.

Antes de crear commits, cherry-picks que generen commits, merge commits, tags, PR o push, verificar la identidad Git contra el `user.name` y `user.email` exactos registrados en PROJECT usando `~/.{{ARNES}}/scripts/Verificar-Identidad-Git.ps1`. Si falta la identidad autorizada, no inferirla ni construir un noreply por cuenta propia: detenerse y pedir el dato. Después de crear commits destinados a transferencia, push, PR o merge, verificar también los SHA o el rango propio a publicar, por ejemplo `origin/dev..HEAD`; no validar toda la historia del producto como si fueran commits nuevos. Un commit nuevo con author o committer no autorizado queda bloqueado hasta corregirlo con aprobación explícita.

En proyectos Next.js, si el dev server se levanta desde una sesión de agente, usar `~/.{{ARNES}}/scripts/Iniciar-Sin-Deteccion-De-Agente.ps1` para ejecutar el comando sin variables de detección de agente en el proceso hijo. Antes de commit, push, PR o transferencia, ejecutar `~/.{{ARNES}}/scripts/Verificar-Artefactos-Agente-Next.ps1` en el repo del producto; si falla, no publicar hasta quitar los artefactos generados y revertir `next-env.d.ts` cuando sólo apunte a `.next/dev/types`.

Las Issues privadas se usan sólo cuando la coordinación cruza WT o proyectos. Son obligatorias para transferencias y dependencias; también corresponden a revisiones o bloqueos compartidos que necesiten otro owner. Un encargo contenido en un solo WT permanece en el prompt y su handoff. La Issue coordina solicitud, destinatario, estado y acuse, pero referencia commits y handoffs en vez de duplicar sus detalles. Usar exclusivamente el repositorio privado configurado en PROJECT, con destino explícito y firma. Si falta, preparar la comunicación local y pedir ese dato; nunca usar el repo del producto por defecto. Notificar a {{APROBADOR}} cada Issue creada. La trazabilidad es asimétrica: la Issue privada puede enlazar PRs o SHAs del producto, pero un PR, commit, changelog o documentación del producto no debe enlazar ni mencionar Issues privadas, repos privados de coordinación, handoffs, WT, chats o rutas del arnés salvo pedido explícito de {{APROBADOR}}.

Antes de crear una Issue, clasificar el destino. Incidencias del producto, coordinación entre WT del producto, dependencias de implementación o transferencias van al canal privado del proyecto configurado en PROJECT. Incidencias del arnés, skills, reglas de WT, handoff, context-resume, worktree-transfer, thread-rescue o comportamiento de Codex/Claude como plataforma van al repo `{{ARNES}}`, no al canal de coordinación del proyecto. Si hay duda, detenerse y preguntar antes de crearla. Si se creó en el destino incorrecto, trasladar el contenido al repo correcto, cerrar la original con enlace y registrar la corrección. Toda Issue creada desde un WT debe incluir firma normalizada: `Proyecto del que viene`, `WT` y `Plataforma`.

## Cerrar por contexto

1. No iniciar trabajo nuevo. Terminar sólo la operación inmediata segura y comprobar carpeta, repo, WT registrado, worker, branch, `HEAD`, `git status` y diff pertinente.
2. Ejecutar las validaciones mínimas que describan el estado que se entrega; registrar fallas y bloqueos. No borrar ni limpiar cambios para producir un falso estado cerrado.
3. Escribir un handoff breve usando `HANDOFF.template.md`: objetivo; estado; cambios; decisiones vigentes; validaciones; pendientes A/B; Issues relevantes; ruta, branch, `HEAD` y archivos modificados; próximo paso sugerido. Indicar qué falta commitear. No copiar conversación ni razonamiento. Si la sesión usó SSH funcionalmente, agregar el contexto SSH heredable mínimo; si no se usó SSH, no diagnosticar ni buscar agentes sólo por rotar.
4. Asignar la versión histórica siguiente leyendo el máximo en `history/`; escribir una copia `NNNN.md` y reemplazar `HANDOFF.md`. Si hay una versión inconsistente, resolverla antes de anunciar el cierre. No versionar el handoff en el repo del producto.
5. Mantener **el mismo WT, branch y worker**. No crear commit, push, PR, Issue ni merge sólo por rotar. Los cambios coherentes sin commit pueden quedar para el chat siguiente.
6. Cambiar el chat `00_[WT]_[NOMBRE]` a `XX_[WT]_[VERSIÓN]_[NOMBRE]` y archivarlo; abrir un chat nuevo `00_[WT]_[NOMBRE]` dentro del mismo proyecto contenedor. El prompt `Continuá WTxx` resuelve la carpeta del WT. Si la interfaz no expone esas acciones, entregar nombres exactos, prompt y pasos manuales; no afirmar que se ejecutaron.
7. Una vez creado o solicitado correctamente el sucesor, `context-handoff` termina el cierre: no espera, lee ni monitorea la respuesta del sucesor por defecto. Sólo puede hacerlo si {{APROBADOR}} lo pide explícitamente o si la creación quedó técnicamente ambigua y no se sabe si el chat existe.
8. Informar al usuario del estado entregado, fallas, Issues creados o existentes que lo afectan y de toda acción manual pendiente. Si se creó un Issue, dar enlace, responsable destinatario y bloqueo.

## Abrir el sucesor

1. Las reglas personales cortas ya están cargadas en la sesión. No volver a pedir la lectura completa de `AGENTS.md`, `WORKFLOW.md` u otros documentos por rutina.
2. Confirmar que carpeta actual, remoto, WT registrado, owner, branch y `HEAD` corresponden al handoff vigente. Leer **sólo** el último `HANDOFF.md` y comprobar `git status` y los cambios relevantes; consultar docs del producto o handoffs históricos sólo si hace falta. Si el handoff trae contexto SSH heredable, comprobar primero el alias, shell/binario, `SSH_AUTH_SOCK` y tipo de agente allí registrados antes de declarar bloqueo de autenticación.
3. Si hubo cambios después del cierre, describir la diferencia y esperar instrucciones antes de asumir un estado anterior. Si no hay handoff (primer chat del WT), verificar Git y consultar el contexto inicial compartible del proyecto.
4. Normalizar el nombre del chat actual a `00_[WT]_[NOMBRE]` antes de responder. Si hay herramienta real para renombrarlo, usarla y verificarla; si no, informar la acción manual pendiente. No dejar el sucesor con el texto del prompt inicial.
5. Responder brevemente: «Listo para continuar en WTxx. Verifiqué ... Quedaron A y B; estaba previsto A. ¿Seguimos con A, con B o con otro encargo?». **Detenerse allí**, aunque el primer mensaje haya sido «Continuá WTxx».

`context-handoff` y `context-resume` no crean filas ni cambian estado, worker, rama o responsabilidad en `OWNERS.md`. Sólo comprueban que el chat corresponde al WT registrado. Una divergencia se informa y se deriva a la operación de ciclo de vida adecuada; nunca se corrige por inferencia.

## Otros cambios de estado

- **Alta de proyecto:** `project-init` crea la identidad estable y el estado personal; no agrega el arnes ni sus archivos al producto.
- **Alta de WT:** `worktree-create` registra una carpeta, rama, worker y responsabilidad únicos antes de comenzar trabajo. Las ramas de WT se crean sin upstream automático hacia la base; cualquier push futuro debe ser explícito. También debe dejar el chat vigente como `00_[WT]_[NOMBRE]` si hay herramienta real para renombrarlo; si no, entrega esa acción manual.
- **Límite activo:** antes de crear o reactivar, contar filas `activo` en `OWNERS.md`. Con cinco, no activar otra: elegir con {{APROBADOR}} cuál pausar o cerrar. Las filas inactivas o cerradas se conservan, pero no cuentan para el límite.
- **Pausa y reactivación:** `worktree-pause` y `worktree-reactivate` alternan `activo`/`inactivo`; worktree-transfer también puede pausar al saliente al ceder responsabilidad. Pausar no exige commit ni integración.
- **Transferencia entre workers:** `worktree-transfer` entrega cambios mediante uno o más commits identificables y una Issue privada. Antes de transferir, valida que el WT solicitado como saliente coincide con el WT/thread actual; ante mismatch no modifica `OWNERS.md`, `HANDOFF.md`, Issues, títulos ni archivo de chats. Si identifica un único thread correcto para el WT solicitado, redirige allí el encargo y termina; si no puede identificarlo con certeza, bloquea y pide abrir o reanudar el WT correcto. No pide autorización para ejecutar una transferencia desde el thread equivocado. Si el receptor ya tiene un WT propio inactivo de una cesión anterior, se verifica y reactiva; si no, se crea uno propio. Incorpora normalmente mediante `cherry-pick`, o continúa desde el commit si {{APROBADOR}} lo decide. Nunca comparte la carpeta ni usa un diff no commiteado. En cesión total, el saliente entrega primero el prompt receptor en el chat actual, se detiene y espera confirmación humana antes de renombrar o archivar; al marcarse `inactivo`, su responsabilidad debe incluir `cedida total a WTxx; issue #n`. No exige PR ni merge a `dev`; eso corresponde a una integración real.
- **Rescate de thread roto:** `thread-rescue` corrige un duplicado funcional de Codex Desktop cuando el chat original quedó roto o inaccesible, por ejemplo `NOMBRE` y `NOMBRE (2)`. Sólo renombra/archiva threads con herramienta real: marca el roto como `NOMBRE [roto archivado YYYY-MM-DD]`, lo archiva, y deja el funcional como `00_[WT]_[NOMBRE]`. El rescate no modifica OWNERS ni handoffs por sí solo; después se continúa desde el funcional con `context-resume`. Si hay más de dos candidatos, ninguno o duda razonable, pide confirmación antes de tocar la interfaz.
- **Cierre:** `worktree-close` marca `cerrado` solamente cuando el trabajo fue integrado o {{APROBADOR}} decidió descartarlo. Al cerrar un WT receptor, busca cedentes asociados en `OWNERS.md` por la marca `cedida total a WTxx; issue #n`; si están `inactivo`, limpios y sin pendientes no transferidos, los cierra en el mismo proceso con motivo `línea cerrada por receptor WTxx`. Si hay cambios, operaciones Git inconclusas o pendientes no transferidos, no cierra ese cedente y lo informa como bloqueo. Cerrar el registro no borra automáticamente carpeta, rama ni commits. Si existe capacidad real de interfaz, el chat saliente se renombra y archiva en la misma ejecución como histórico `XX_[WT]_[VERSIÓN]_[NOMBRE]`; no se deja el archivado como segundo paso manual para preservar visibilidad del resumen. Sólo queda acción manual si la interfaz no permite archivar o si el archivado falla explícitamente. No existe prefijo `CL_...` para chats, porque el cierre del WT ya queda registrado en `OWNERS.md` y `HANDOFF.md`.
- **Integración real:** el worker puede preparar commits, push y PR a `dev` en su feature; espera aprobación expresa para ejecutar el merge. Antes de crear o actualizar un PR del producto, revisar título y cuerpo para quitar referencias a coordinación privada (`owner/repo#n`, URLs del repo privado, rutas `~/.{{ARNES}}`, handoffs, OWNERS, WT o chats). Si se detecta una referencia privada después de publicar el PR, editar el PR del producto y registrar la corrección en la Issue privada. Promover `dev` a `main` requiere aprobación expresa de {{APROBADOR}}; sin ella ningún worker la ejecuta. Cuando el trabajo ya esté integrado o descartado, cerrar el WT, actualizar owners y avisar a los workers afectados.
- **Falta de capacidad UI:** las skills sólo gestionan la interfaz si disponen de herramientas para renombrar, archivar y abrir el chat. Si no, entregan el paquete manual completo.

## Entrega y recepción

Transferir sólo entre WT o clones del mismo producto. Una extracción sanitizada con historia independiente no se sincroniza con el original mediante este procedimiento.

El saliente registra commits en orden, base, dependencias, validaciones y handoff, y abre o actualiza la Issue de transferencia. La Issue debe incluir un bloque **Prompt para el receptor** listo para copiar en el chat receptor, con comando de transferencia, enlace a la Issue, WT receptor esperado, creación o reactivación requerida, base/rama sugerida, commits en orden, validaciones esperadas y límites explícitos. El prompt se formatea según destino: Codex usa `$worktree-transfer` y Claude usa `/worktree-transfer`, con `Destino: Codex` o `Destino: Claude` explícito. En cesión total, antes de archivar el thread saliente, el saliente debe mostrar en el chat actual el enlace a la Issue, estado de la cesión, prompt receptor y acciones pendientes; luego se detiene y espera confirmación humana de {{APROBADOR}} (`listo`, `completado`, `archivar` o equivalente). Si se interrumpe antes del archivado, la Issue y el handoff deben alcanzar para recuperar el estado. El receptor incorpora en su propio WT y registra la correspondencia SHA de origen → SHA recibido. Un cherry-pick puede producir un SHA diferente. La transferencia permanece preparada o bloqueada hasta el acuse del receptor en la Issue.

La redirección por thread equivocado no ejecuta la transferencia: sólo envía o direcciona el encargo al thread correcto cuando éste es inequívoco. El thread equivocado termina informando que no ejecutó cambios. Si hay más de un candidato, ninguno o cualquier duda razonable, se bloquea sin preguntar por autorización y se indica abrir o reanudar el WT correcto.

Antes de incorporar, el receptor verifica un estado limpio, ausencia de merge/rebase/cherry-pick en curso y disponibilidad de todos los commits. Si existe un WT propio inactivo, comprueba su rama, HEAD, divergencias y commits ya recibidos antes de reactivarlo; no crea otro por rutina. Un reintento consulta el acuse y los cambios ya incorporados para evitar duplicados. Ante conflictos se registra el estado y se detiene sin descartar cambios. En una cesión total, pausar al saliente antes de activar al receptor; el chat saliente debe quedar `IN_[WT]_[NOMBRE]` y archivado si la interfaz lo permite sólo después de la confirmación humana, o como acción manual pendiente explícita. No dejarlo como `00_...`. Cuando el receptor cierre la línea, `worktree-close` puede cerrar también al cedente inactivo asociado sin abrir otro chat del saliente. No escribe un handoff nuevo obligatorio del cedente: registra los cedentes cerrados o bloqueados en el handoff del receptor y en `OWNERS.md`, salvo pedido explícito o información relevante que deba quedar en el cedente. Una entrega parcial conserva ambas responsabilidades y se cierra por separado; no usa la marca de cesión total.
